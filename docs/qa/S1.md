S1(저장소 골격)을 만들면서 오간 질문과 답이다. 시간 순으로 적는다. 사용자 발언은 원문 그대로, Claude 답은 요약이다. 기록 규칙은 [process.md](../process.md#질의답-기록)에 있다.

이 저장소 이전의 질의답(6주 계획을 세운 대화)은 별도 문서에서 진행했고 여기 남아 있지 않다. 그 결과가 [plan.md](../plan.md)다.

### 4. 사용자: Linux VM 사용 제안

> 그리고 mac으로 그냥 쓰면 애매하다면, 전에 QEM이었나 거기에 리눅스 구성한게 있을텐데

Claude 답:

- Mac mini 위에 QEMU(libvirt)로 도는 Ubuntu 26.04 LTS arm64 VM이 있다. 4코어, 메모리 3.8GB, 디스크 여유 22GB다.
- 이미 gcc 15.2, clang 21.1.8, cmake 4.2.3, ninja 1.13.2, git, python3, tcpdump가 설치돼 있다. libpcap-dev는 없어서 S2 전에 설치가 필요하다.

- 반대로 bpf, libproc, kqueue처럼 실제 감시 대상은 macOS에만 있다.
- 추천은 Mac mini를 기본으로 두고 Linux VM을 보조로 쓰는 것이다. 저장소 원본은 Mac mini에 두고, VM은 GitHub에서 받아 빌드한다.

### 10. 사용자: GNU 확장, 감시 대상, 개념 질문

> -std=gnu17로, 커널 호환성에 혹함
>
> 감시 대상:
> 그럼 Mac에 기반을 두고 별도로 감시하도록해야하나. 근데 뭘 감시하는거지?
>
> sanitizer:
> ASan, UBSan, MSan 기능 나눠서 각각 설명해
>
> 테스트:
> 각각 구성 예시 줄래?

Claude 답:

- portscope는 도구가 돌고 있는 기기에서 어떤 프로세스가 어느 목적지로 몇 개 연결하는지 본다.
- Mac mini에는 Docker 컨테이너가 여럿 돌고 있다. Mac에서 보면 이들의 외부 연결이 Docker 프로세스 하나로 묶여 구분되지 않는다.
- 배치 선택지를 제시했다: Mac 호스트 / Docker 안 / VM 안.
- sanitizer 설명:
    - ASan: 접근 금지 구역을 두고 메모리 접근마다 검사해 버퍼 넘침과 해제 후 사용을 잡는다.
    - UBSan: 연산 앞에 조건 검사를 넣어 정의되지 않은 동작을 잡는다.
    - MSan: 바이트마다 초기화 여부를 추적해 초기화 안 한 값 사용을 잡는다. clang과 Linux 전용이고 별도 빌드가 필요하다.
- 같은 테스트("IHL이 5보다 작으면 거부")를 최소 매크로, Unity, cmocka로 각각 쓴 예시를 보였다.

바뀐 것: C 표준을 `-std=gnu17`로 확정.

> 감시 대상:
> 너가 하려는게 데몬 아닌가? 각 컨테이너에 넣고 거기서 MAC 혹은 다른 컨테이너와 통신하는거. 맞으면 그게 깔끔해 보이는데
>
> sanitizer:
> 다 넣어. 컴파일 시간 늘어나는게 치명적인 것도 아니고, 나중에 너무 느려지면 조정하지 뭐
>
> 테스트
> :cmocka가 보다 다양한 테스트 값을 넣어서 유동적으로 테스트할 수 있는거 아닌가? 맞다면 이거로

Claude 답:

- portscope는 데몬이 맞다. 배치 방식은 두 가지가 있다. 하나는 컨테이너마다 붙이는 방식이고, 다른 하나는 Docker 안에 하나만 두는 방식이다.
- 결과를 수집기로 보내는 구간에 프로젝트 2의 mTLS를 쓸 수 있다.
- 여러 입력값으로 같은 테스트를 돌리는 것은 세 도구 모두 된다. cmocka만의 차이는 의존 함수가 돌려줄 값을 테스트에서 정하는 것이다.

바뀐 것: sanitizer를 ASan+UBSan + MSan 별도 빌드로 확정.

> DaemonSet: 그럼 너는 사이드카를 추천하는거야?
> 명세를 Claude가 씀: 괜찮아. 결국 내가 꼼꼼히 확인했으니까
> Mac 원본 + 공유 폴더: 이건 답변 받고 추후에 다시 답변할게

Claude 답:

- 9p와 sshfs의 트레이드오프를 비교했다. 비교 항목은 설정, 보안, 끊김과 재부팅, 속도다.
- Kbuild는 커널과 커널 모듈용이라 독립된 사용자 공간 프로그램을 빌드하는 데는 쓸 수 없다. 대안은 세 가지다.
    - CMake에서 Kbuild를 호출한다.
    - 전체를 Make로 바꾼다.
    - 커널 작업이 생길 때 정한다.
- 연결 감시 쪽 커널 작업은 eBPF일 가능성이 크고, eBPF는 Kbuild 없이 clang으로 빌드한다.
- CI 러너는 x86_64이고 실제 실행 환경(Apple Silicon 위 Docker)은 arm64다. 둘은 `char` 부호처럼 다르게 동작하는 부분이 있다.
- sanitizer 빌드와 테스트 시간을 대략 예상했다.
- DaemonSet 피드백은 사이드카 추천이 아니다. 고른 쪽이 감수할 비용을 적은 것이다.

바뀐 것: [decisions.md](../decisions.md)에 다음을 반영했다.

- C 표준 이유 변경
- 경고 수준 이유 변경
- `-Werror`를 "안 함"으로 변경
- Unity 이유 추가
- 명세 작성 이유 추가
- "CI CPU 아키텍처" 항목 추가(미정)

- sshfs 구성 계획을 제시했다.

바뀐 것: [decisions.md](../decisions.md)에 다음을 반영했다.

- 공유 방식 sshfs 확정
- CI CPU 아키텍처 arm64 확정
- "커널 빌드 대응" 항목 추가(확인 중)
