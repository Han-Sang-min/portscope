# 진행 방식

구현은 Claude가 맡는다. 구성 방향은 직접 정한다. 구성된 내용에 대한 질문에 모두 답할 수 있을 만큼 개념을 학습한다. 작업은 프로토콜 계층 순서로 나눈다. 결정은 제시된 선택지에서 고르고, 구현은 테스트 명세에서 시작한다. 학습은 코드에서 개념으로 거슬러 올라가고, 복기는 기존에 쓰는 방식으로 한다.

## 원칙

- 실행 전에 계획을 확인한다. Claude는 파일, 저장소, 설치 작업을 하기 전에 무엇을 할지 먼저 보여주고 확인을 받는다.
- 추천하지 않는다. Claude는 선택지와 차이만 제시한다. 개념을 모르는 항목은 고르기 전에 설명을 요청한다.

## 단계마다의 순서

1. 결정: Claude가 선택지와 차이를 제시하고 직접 고른다. 고른 것과 이유는 [decisions.md](decisions.md)에 적는다.
2. 명세: Claude가 테스트 케이스를 말로 적고, 직접 확인한다. 예: "IHL이 5보다 작으면 버린다".
3. 구현: Claude가 명세로 테스트 코드와 구현을 쓴다.
4. 문서: Claude가 단계 문서(`steps/<단계>.md`)를 쓴다.
5. 학습: 단계 문서의 추적표를 따라 코드에서 개념으로 거슬러 올라간다.
6. 복기: 기존 방식으로 한다.

명세는 구현 전에 쓰므로 빠지는 케이스가 생긴다. 구현 중 추가한 케이스는 단계 문서에 따로 적고, 다음 명세를 보완하는 데 쓴다.

## 질의답 기록

단계를 만들면서 오간 질문과 답은 `qa/<단계>.md`에 시간 순으로 남긴다. 결정 질문, 계획 요청, 학습 중 질문, 진행 방식에 대한 교정이 모두 들어간다.

- 사용자 발언은 원문 그대로, Claude 답은 요약으로 적는다.
- 각 항목은 무엇이 바뀌었는지(결정, 파일, 계획)로 끝난다.
- 공개 저장소이므로 IP, 계정, 개인 서비스 세부는 적지 않는다.

## 단계 문서 구성

[steps/_template.md](steps/_template.md)를 복사해 쓴다.

1. 범위: 만든 것과 만들지 않은 것
2. 적용한 결정: 결정 항목, 고른 것, 직접 적은 이유
3. 명세와 테스트 대응: 명세의 케이스마다 그것을 확인하는 테스트 이름
4. 명세에 없던 케이스: 구현 중 추가한 케이스와 이유
5. 코드 → 개념 추적표: `파일:줄`, 코드, 왜 있나, 개념, 참고 자료(RFC 절 번호 등)
6. 다음 단계로 넘기는 것: 미해결 항목, 알려진 한계

## 한계

- 질문에 답할 수 있다고 직접 짤 수 있는 것은 아니다. 직접 짜는 연습은 따로 한다.
- 결정을 개념 학습 전에 내린다. 학습 후 다시 보고 바꿀 결정은 다음 단계 결정 때 바꾼다.
- 명세도 Claude가 쓰므로, 명세와 구현이 같은 오해를 공유할 수 있다. 명세 확인 단계에서 걸러낸다.
